
# Sparkle auto-updates

## Problem

VibePulse ships signed, notarized DMGs through GitHub Releases, but users had
to notice a new release and manually download and reinstall it. This document
covers in-app update delivery via Sparkle 2.x (`https://sparkle-project.org/`),
the standard macOS auto-update framework.

## Non-goals

- Delta updates (binary diffs). A full DMG per release is fine at VibePulse's
  size.
- Beta or prerelease channels. There is a single stable feed.
- A self-hosted update server. GitHub Releases hosts the DMG and the appcast.
- In-app changelog browsing. Release notes render in Sparkle's own dialog;
  GitHub remains the source of truth for the release body.

## User experience

Sparkle shows its native dialog with rendered release notes and **Install
Update**, **Remind Me Later**, and **Skip This Version** buttons. On
**Install**, Sparkle downloads the DMG, verifies the EdDSA signature, replaces
the app bundle via its XPC helper, and relaunches into the new version.

A "Check for Updates…" button sits in the menu bar popover controls row next
to Refresh and Settings. It calls the user-initiated check API, which shows a
"You're up to date" dialog when nothing is newer.

Packaged builds carry a Sparkle feed; development builds built with `swift
run` have no bundled `Info.plist` and therefore no `SUFeedURL` key.
`UpdaterController` checks for that key at construction time and leaves its
internal `SPUStandardUpdaterController` nil when it is absent, so `swift run`
never starts Sparkle or shows its error alert. The "Check for Updates…" button
is disabled whenever the controller has no live updater
(`UpdaterController.isAvailable`).

When automatic checks are enabled (the Info.plist default), the app also runs
a silent background check shortly after launch: `UpdaterController.init`
inspects `updater.automaticallyChecksForUpdates` and only calls
`checkForUpdatesInBackground()` when that persisted preference is true, so a
user who disabled automatic checks through Sparkle's own UI is not
overridden. Sparkle's own scheduler then repeats the check every 24 hours via
`SUScheduledCheckInterval`.

## Client-side architecture

- Sparkle 2.9.1 is a SwiftPM binary dependency pinned with `exact:` in
  `Package.swift`.
- `Sources/VibePulse/Services/UpdaterController.swift` is a thin wrapper
  around `SPUStandardUpdaterController`, instantiated once by
  `VibePulseApp` and held for the app's lifetime via `@StateObject`.
- `Info.plist`, generated by `scripts/build_dmg.sh`, carries four Sparkle
  keys: `SUFeedURL` (the latest-release appcast URL), `SUPublicEDKey` (the
  base64 Ed25519 public key), `SUEnableAutomaticChecks` (`true`), and
  `SUScheduledCheckInterval` (86400 seconds).

## Bundle embedding

VibePulse builds via `swift build -c release` plus a hand-written
`scripts/build_dmg.sh`, not Xcode, so nothing embeds frameworks into the app
bundle automatically. `build_dmg.sh` does this itself, after building the
executable and before signing:

1. Locates the macOS slice of the Sparkle xcframework with `find
   .build/artifacts -type d -path '*macos-arm64_x86_64/Sparkle.framework'`,
   failing fast if it finds zero or more than one match (the SwiftPM artifact
   path varies with package-manager internals).
2. Copies `Sparkle.framework` into
   `VibePulse.app/Contents/Frameworks/Sparkle.framework` with `cp -R`.
3. Rewrites the executable's runtime search path. `swift build` links
   Sparkle via its absolute `.build/artifacts/...` path, which only resolves
   on the build machine. `build_dmg.sh` discovers that absolute install name
   with `otool -L ... | grep Sparkle`, then uses `install_name_tool` to add
   an `@executable_path/../Frameworks` rpath and retarget the Sparkle
   reference to `@rpath/Sparkle.framework/Versions/B/Sparkle`.
4. Verifies the rewrite before signing: `otool -L` must show the `@rpath/`
   reference and `otool -l ... | grep -A2 LC_RPATH` must contain
   `@executable_path/../Frameworks`. The script aborts with a clear error if
   either check fails, so a broken rewrite is never signed, notarized, or
   shipped.
5. Signs nested components inside-out, in dependency order, before signing
   the outer app: each XPC service under
   `Sparkle.framework/Versions/B/XPCServices/*.xpc`, then the bundled
   `Autoupdate` helper binary and `Updater.app` (Sparkle 2.9.1's layout —
   `Autoupdate` is a bare Mach-O, not a nested `.app`), then
   `Sparkle.framework` itself, then `VibePulse.app`. Each `codesign` call
   uses `--options runtime --timestamp --sign`; `--deep` is not used for
   signing because it does not handle Sparkle's nested helpers correctly.
   `codesign --verify --deep --strict --verbose=2 VibePulse.app` runs last
   as a final check (`--deep` is fine for verification).

A cold-start smoke test (double-clicking the built `.app`, not running it
in place) is the only check that catches a bad rpath rewrite: signing and
notarization both pass on a bundle that cannot actually find Sparkle at
launch, so a dyld "library not loaded" error only shows up when the app is
actually launched from its final location.

## Release pipeline: draft-then-publish

The appcast needs GitHub Release metadata — the release body and the
stapled DMG's final download URL — that does not exist until the Release
object is created. Creating the release first and attaching the appcast
after it would open a window where `releases/latest/download/appcast.xml`
404s for any Sparkle client that checks during that window. GitHub's
`/releases/latest` endpoint resolves to the newest release that is neither a
draft nor a prerelease, so both `.github/workflows/release.yml` and
`scripts/release_local.sh` (the CI and local release paths) avoid the window
by running three phases:

1. **Create a draft release** with the signed, notarized DMG and
   `SHA256SUMS` attached, with `--generate-notes` (CI uses
   `generate_release_notes: true` on `softprops/action-gh-release`) so the
   release body is populated before appcast generation reads it.
2. **Generate and attach the appcast while the release is still a draft.**
   `scripts/generate_appcast.sh <version>` computes the DMG's SHA-256 and
   byte size, signs it with `sign_update` (located anywhere under
   `.build/artifacts` by name, skipping `old_dsa_scripts`), reads the
   release body with `gh release view --json body` (draft releases are
   readable by the repo owner), converts it to HTML via `gh api -X POST
   /markdown -F text=@-`, and emits `dist/appcast.xml`. It validates the
   result with `xmllint --noout` and a `sparkle:edSignature` grep before
   exiting. The appcast is then uploaded to the draft with `gh release
   upload --clobber`, which is idempotent on reruns.
3. **Publish the draft:** `gh release edit <version> --draft=false`. This
   single step is the only point at which `releases/latest` can change, and
   by this point the DMG and the appcast are already attached. A Sparkle
   client checking for updates sees either the fully-assembled previous
   release or the fully-assembled new one, never a half-built one.

If the job fails between uploading the appcast and publishing, the draft
release sits with both assets attached and the previous release stays
"latest," so no user is affected; rerunning the release job or manually
running `gh release edit <version> --draft=false` recovers.

### Release-notes source and fallback

The appcast's `<description>` uses the GitHub Release body converted to
HTML. If `gh api /markdown` fails or returns empty, `generate_appcast.sh`
falls back to the raw markdown wrapped in a `<pre>` CDATA block, then to a
bare `"Release v<version>"` string. Release-notes rendering never blocks a
release.

For local testing without a real GitHub Release, `generate_appcast.sh`
accepts `APPCAST_RELEASE_BODY_FILE` pointing at a markdown file on disk and
reads the body from there instead of calling `gh release view`.

## Version comparison

Sparkle compares the appcast's `sparkle:version` against the app's
`CFBundleVersion`, not the marketing `CFBundleShortVersionString`.
`build_dmg.sh` currently sets both plist fields to the same release-tag
value, so this distinction does not matter today, but if they ever diverge
(for example, switching to a monotonic build-number scheme), only the
`CFBundleVersion`-derived value in the appcast affects update decisions.

## Key management and rotation

`Sparkle.framework/Versions/B/Resources/generate_keys` creates the Ed25519
keypair once, storing the private key in the login Keychain and printing the
base64 public key. The public key is committed as a literal string in the
`SUPublicEDKey` entry `build_dmg.sh` writes into `Info.plist` — it is public
by design. The private key is extracted from the Keychain and stored as the
`SPARKLE_ED_PRIVATE_KEY` GitHub secret (see
[docs/github-actions-release.md](../github-actions-release.md) for the
setup commands).

`generate_appcast.sh` picks its key source from the environment: in CI,
`SPARKLE_ED_PRIVATE_KEY` is written to a temp file and passed to
`sign_update --ed-key-file`, then deleted; locally, the variable is normally
unset and `sign_update` falls back to the login Keychain where
`generate_keys` stored it.

**Planned rotation (old key still available):** ship one transition release
signed with the *old* private key but carrying the *new* `SUPublicEDKey` in
its Info.plist. Clients on the previous version verify this release against
their existing key, install it, and thereby pick up the new public key;
every release after that is signed with the new key. This has a real
limitation: because the appcast is a single-item feed (see Non-goals), the
transition release's item disappears from the feed as soon as the next
release ships. Any user who did not check in during that window sees only a
new-key-signed release, which their embedded (old) key cannot verify, and
must manually reinstall. Routine rotations should be announced in release
notes with a buffer of at least one scheduled-check cycle (realistically a
couple of weeks) between the transition release and the next one. Making
this fully safe would require migrating to a multi-item aggregated appcast
so the transition release stays visible for longer; that migration is
deferred until it is actually needed.

**Compromised or lost key:** generate a new pair, update both
`SUPublicEDKey` and the `SPARKLE_ED_PRIVATE_KEY` secret, and ship. Every
existing user's Sparkle client refuses the new signature because it cannot
be verified against their embedded old public key, so they must manually
download and install once from GitHub Releases; updates resume normally
after that. This path is for incident response only, not routine rotation.

## No partial-disable flag

There is no `ENABLE_SPARKLE`-style toggle gating the shell scripts.
`UpdaterController` is a hard dependency instantiated at launch, and
disabling only the shell-script half would leave a client that expects an
embedded framework and advertises a feed URL it cannot use, producing
runtime errors instead of a clean pre-Sparkle build. If updater plumbing
ever blocks a release, the recovery path is to revert the Sparkle commits on
a hotfix branch and release from there.

## Known limitations

- Users on versions before Sparkle was added have no embedded framework and
  must install the first Sparkle-enabled release manually; every version
  after that updates in-app.
- The appcast is a single-item feed; it has no version history, which is
  what limits the planned-rotation window described above.
- `sign_update`'s exact CLI flags and nested-helper file names are tied to
  the pinned Sparkle version (2.9.1) and have already changed once from
  earlier assumptions (`Autoupdate.app` versus a bare `Autoupdate` binary
  plus `Updater.app`); upgrading Sparkle may require re-checking both.
